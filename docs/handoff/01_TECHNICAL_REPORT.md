# LeaseRadar（铺讯）技术报告与开发规格

版本 v1.0｜2026-10-10｜对象：Codex开发者、项目负责人、试用用户

## 1. 产品目标与成功定义

### 1.1 要解决的工作问题

门店拓展人员需要浏览多个产权交易、农村资产、高校及企业网站。公告分散、格式不一致，有些关键信息在图片或附件；人工发现较晚，可能错过报名。负责人还需要按位置、面积、租金、用途比较候选铺位。

系统目标：在明确接入的来源范围内持续发现信息，提取可核对的字段，筛出值得跟进的候选，及时通知并保存跟进结果。不能承诺覆盖互联网全部房源，也不能保证用户一定租到铺位。

产品北极星指标：每周在报名截止前及时交付给用户、且被用户认定值得跟进的独立候选数量。辅指标：发现延迟、匹配召回率、通知准确率、用户处理时间、来源有效覆盖率。

### 1.2 实际使用闭环

管理员添加并验证来源 → 负责人保存订阅条件与通知渠道 → 后台常驻检查 → 新公告结构化与去重 → 条件匹配 → 及时提醒 → 手机查看依据与截止时间 → 标记联系/看铺/不合适 → 每日摘要和历史比较。

负责人第一次使用应在10分钟内完成订阅并看到首次同步的候选，具体时间在试用中验证。初次大量历史数据走摘要，不把几百条存量公告逐条推送。之后新增高匹配候选才进入即时队列。

### 1.3 用户与权限

首版是单团队工具，不做复杂SaaS。admin负责来源、凭据、用户、运行状态；member负责订阅、收藏、比较与跟进。邀请建号或管理员创建账号，登录限速、强密码哈希、HttpOnly会话Cookie、CSRF防护。外部通知中的详情链接仍需登录；不要把联系方式和私人跟进笔记放在公开页面。

## 4. 用户界面与业务流程

### 4.1 首页与列表

首页优先显示“新增匹配”“即将报名截止”“待确认条件”“采集异常”。显示最近成功同步时间与覆盖来源数。未同步成功不能显示“今天没有新房源”。

列表按发现时间/报名剩余时间/可比租金排序。筛选地区、面积上下限、价格口径、类型、所在环境和状态。支持关键词与地址搜索。列表展示：地址、面积、原价及口径、匹配等级、报名截止、来源、最后核验时间。未知值不当成0。

### 4.2 详情与比较

详情分为铺位资料、原始来源、条件匹配、费用、挂牌时间线、跟进记录。重要字段点击后定位原文段落、附件页/表格单元格或OCR区域。并列比较2–5条，展示相同字段、差异、缺失项和价格计算过程。

物业类型与所在环境为两个字段：shop/commercial_unit/apartment/office/warehouse等；campus/apartment_building/street/market等。公寓楼内的店面是shop+apartment_building，不是apartment。

跟进状态：未查看、已查看、待联系、已联系、预约看铺、放弃、已成交。用户放弃需可选原因，例如太远、用途限制、价格高、信息过期。该反馈先用于报告，不自动更改硬条件。

### 4.3 订阅与提醒

表单作为权威需求编辑界面；自然语言只生成草稿，用户看到转换后的条件并保存。硬条件用于排除，偏好用于排序。条件未知时按用户设置进入待确认摘要或排除，不算明确匹配。

提醒模板：新增/变更原因、地址、面积、价格及性质、符合哪些条件、哪些待确认、报名截止和来源时间、详情与原文链接。提供已读、收藏、停止该订阅等操作。

即时事件：新增高匹配、关注项实质降价、用途限制变化、重新挂牌且仍符合、报名延期。一般候选走每日摘要。截止提醒默认提前72/24小时，须用户可配置；已关闭、已放弃、已成交不再推催办。关闭或撤回事件对关注用户可发送状态通知。

通道首选网页+SMTP邮件，或负责人已有的企业微信/钉钉Webhook择一；必须确认渠道可用后配置，不宣称普通个人微信可直接推送。未配置密钥使用local_test_sink，界面明确为本地测试。开发测试不向真实负责人发消息；投产配置的目标地址是后续授权步骤。

## 5. 技术架构与技术栈

采用模块化单体+任务worker，避免首版微服务。建议基线：Python3.12、FastAPI/Pydantic、SQLAlchemy/Alembic、PostgreSQL、Celery+Redis、React/TypeScript/Vite、Docker Compose。依赖兼容组合在首次开发时核验并锁定，不无条件升级到最新。

处理链：调度器 → 来源适配器 → 原文/附件快照 → 解析与提取 → 校验/证据 → 实体关联与挂牌版本 → 订阅匹配 → 数据库事务outbox → 通知worker → 用户收件箱。

API与worker共享核心领域模块；前端经同域反向代理访问API。Celery beat只运行一个实例，worker可扩展，来源级数据库租约或锁禁止并发重叠；任务设计按至少一次投递处理，靠幂等约束保持业务一致。Redis不是记录真相，PostgreSQL为权威。

网页读取先HTTP客户端+HTML解析；仅动态页面采用隔离的Playwright Chromium，运行在受限worker中。附件按MIME与文件魔数处理，不执行宏。OCR/LLM作为可选后端；不开模型也能运行固定规则、手工导入和演示。

初版搜索用PostgreSQL字段索引及pg_trgm/关键词；中文用字段过滤、子串或验证后的分词，不假设默认全文检索自动支持中文。暂不引入Elasticsearch或向量库。

建议代码目录：

```text
backend/app/
  api/ auth/ db/ models/
  collectors/ parsers/ extraction/
  normalization/ resolution/ matching/
  monitoring/ notifications/ audit/
backend/tests/
frontend/src/
sources/ fixtures/ benchmarks/ docs/
docker-compose.yml
```

以上是项目设计而非已经上线的架构。

## 6. 多来源接入与监测

### 6.1 Source Adapter统一契约

建议Python协议，类型由Pydantic定义：

```python
class SourceAdapter(Protocol):
    async def discover(self, ctx, cursor=None) -> DiscoveryPage: ...
    async def fetch(self, ref, ctx) -> RawDocument: ...
    async def parse(self, document, ctx) -> ParsedAnnouncement: ...
```

DiscoveryPage包括refs、next_cursor、coverage_complete与warnings；RawDocument包括请求/最终URL、状态码、抓取时间、正文hash、响应头、快照引用；ParsedAnnouncement含公告正文、来源状态、批次编号、附件与多个lot。分页游标只在持久化完成后提交；中途失败不得跳过未入库页。

提供adapter版本、配置schema、fixture与contract tests。新网站接入流程：检查公开访问/规则 → 识别列表/分页/详情 → 采集真实样本 → 编写适配器 → 标注关键字段 → 验证增量与状态 → 小流量运行 → 启用订阅。不要编造CSS选择器、隐藏接口或分页参数。

### 6.2 频率、增量与补漏

默认建议每来源30分钟，可按源规则改为15–60分钟。请求间隔默认2–5秒并加抖动，每域并发1；收到429按Retry-After退避，403暂停并记录阻塞。该频率是初始配置，不是网站许可或实时保证。

优先列表查新；支持ETag/Last-Modified的来源使用条件请求。详情靠内容hash决定是否重新提取，但不能忽略状态字段动态变化。活跃及关注记录定期复查；每日做深分页回扫，避免只看第一页漏掉回填或置顶变化。恢复服务后回扫最近窗口及分页覆盖，记录缺失时段。

必须跟踪：last_attempt_at、last_success_at、连续失败数、覆盖页数、发现数、解析错误率、任务耗时、next_run_at。任务成功意味着完成预定覆盖，不是HTTP200。空结果/关键选择器失效需与已知空页面fixture区分，异常空列表应降级并告警。

不要求每次全站扫描。增加来源时共享原始采集供多订阅复用，不能每个用户各自抓一遍。

### 6.3 时效承诺

将发现延迟拆为网站可观测等待、调度等待、抓取/解析、通知队列。内部目标：原始快照已成功存储后到通知入队P95≤5分钟（规定测试负载下），入队到通道接受P95≤2分钟。若30分钟轮询，不能对用户承诺每条公告5分钟内发现。

网站只提供发布日期时，只能测粗粒度日期或从首次可观测时刻测量。一次页面404不直接判定撤回；保留last_seen并复核，优先采用来源明确的撤回/成交状态。

| notification_outbox | event、subscription、channel、destination_ref、state、attempts、next_retry |

| correction/audit | 人工改动、原值、新值、依据、操作者、关联版本 |

金额用Decimal/PostgreSQL NUMERIC，不用float。面积数值+单位+approx标记；非㎡记录不能混进面积筛选。日期时间存UTC且带来源时区，前端Asia/Shanghai；只有日期的截止时间标记precision=date，提醒保守处理，不擅自补23:59当作原文事实。

明确三个层次：资产（实体铺位）、挂牌批次（一次出租机会）、来源记录（不同网站文章）。同资产重新挂牌不是简单重复；同一挂牌多源转载通常不是新机会。多间整体出租的lot保存bundle和成员信息，不能把整体价分配给每个成员导致虚假低价。

原文快照仅在团队授权范围展示，公开仓库使用合成fixture或可再分发样本及来源说明。建议快照默认90天，业务历史默认一年，可配置；记录敏感信息删除与日志脱敏。

## 8. 信息提取、AI与人工纠正

处理顺序：DOM/表格确定性解析 → PDF文字/表格、DOCX、XLSX → OCR扫描/图片 → 规则单位解析 → 可选LLM补充复杂约束 → Pydantic校验 → 证据关联 → 人工待审核队列。

模型输出结构化JSON，必须包含对应证据引用。无证据的关键值改unknown，不用模型“猜”。置信度仅为工程提示，未经校准不能称为准确概率。用途、截止日期、价格周期低置信度或冲突时进入待核对，不能发送明确符合的即时消息。

LLM按document_hash+prompt_version+model_id+schema_version缓存；设置每日预算、重试上限、超时及开关。先规则后模型，成本记录每公告与每日总量。预算耗尽仍采集原文，解释字段待处理，恢复后补处理。

外部内容是不可信数据；LLM提取器不得获得发消息、执行代码、改数据库或访问任意URL权限，页面中的“忽略指令”等只视为文本。模型只返回候选字段，程序做校验、换算和匹配。

人工改字段需依据、审计及新版本；来源再次更新时不静默覆盖人工纠正，创建冲突待审。未知经营条件可以人工联系核实并记录用户提供的来源，但不能伪装为网站原文。

## 9. 价格标准化与比价规则

必须保存raw_amount、raw_text、currency、price_kind（起拍/挂牌/成交）、period_basis、rent_term、escalation、fees、evidence和normalization_status。

确定规则：月租R → annual=12R；首年租金A → first_year_monthly=A/12；元/㎡/月P且面积S → monthly=P×S；元/㎡/天按用户可见的365/12天折算约值，明确为假设，不是合同月租。

总租期金额T与确定N个月 → 可显示average_monthly=T/N，名称必须是“租期平均月租”，不能冒充首年月租。若存在递增、免租或分段付款，优先实际租金序列；不明确则未知。五年租赁权不意味着网页价格是五年总价。

若首年A、每年递增g、N年且明确每年复利：total=A×sum((1+g)^k,k=0..N-1)。若每三年、固定金额或分段递增，按实际条款计算，不套用上述公式。非整年和免租期按明确条款，否则不算精确总成本。

单位面积月租=相同面积口径的monthly/S，S必须>0。按price_kind及basis分组比较，默认不把成交价和起拍价混排。费用分别显示已知租金支出、不可退费用、可退保证金的现金占用；缺失费用意味着成本不完整，不能输出最低总成本结论。

示例测试：首年120000、面积60㎡ → 10000/月、约166.67元/㎡/月。标题“五年租赁权”、价格120000、周期未知 → 不换算。不以这两个示例作为真实房源。

## 10. 实体去重、冲突与变化识别

候选生成按来源项目编号、地区、规范地址和铺号；强身份匹配优先项目/lot映射。地址标准化保留楼栋、单元、铺号；门牌11号与111号不能相似度高就合并。面积接近、同出租方和时间窗口只能作辅助证据。

实现可解释分数与三段决策：高置信且无硬冲突自动关联、中等进入人工队列、低分保留独立。阈值用标注集校准，首版保守；每次合并可撤销。禁止把地址相似当作同一资产的充分条件。

同一项目整租与分租建立关系不直接合并。多源冲突保留每源观察，按发布时间、直接发布单位、字段证据和新鲜度决定展示值；无法判断时并列冲突，不简单“最后抓到的优先”。

变化只比较规范业务字段，忽略广告、访问计数和排版。实质事件包括新增挂牌、明确降价、用途/报名资格变化、报名延期、成交/撤回、重新挂牌。新抓取快照不等于新事件；模型版本升级提取差异标为reprocessing，不伪称市场降价。

## 11. 匹配与通知可靠性

每个条件三值：pass/fail/unknown。硬条件fail即排除；unknown按订阅策略进入待确认，整体不能等同pass。偏好只影响排序，不越过硬条件。面积上下界含端点、金额统一币种/口径、地址按可靠地区字段；“允许饮品”与“允许油烟餐饮”分开。

过报名期限且无明确延期的记录不作为可报名新增推荐；截止未知可待确认。新订阅建立baseline，历史只摘要；策略编辑按rematch事件汇总，避免全部重新即时推送。

事件、版本和outbox在同一数据库事务中提交。去重键至少包含subscription_id、event_id、channel、destination；数据库unique保证并发重复任务不生成重复outbox。worker用锁/租约领取，按退避重试并进入死信队列，可管理员重放。

外部通道超时可能已接受消息，不能保证端到端绝对一次。支持provider幂等键时使用；不支持时记录ambiguous并按策略复核/重试，测试并公开残余重复风险。区分queued、sending、accepted、delivered（仅有回执）、failed；SMTP接受不等于负责人已阅读。

延期需取消旧截止任务并建立新提醒。日摘要标记覆盖时间窗与异常来源；静默时段用户可配置紧急覆盖，否则延后推送并保留首次发现时间。

## 13. 部署、运行成本与安全边界

部署：一台常驻Linux服务器，Compose运行proxy/web、api、worker、beat、Postgres、Redis、持久化文件卷。初始容量假设5个来源、每天≤300条新增/变化、≤10个用户；2–4核/4–8GB作为待压测起点，不作为性能保证。浏览器和OCR单独限并发。

静态网页托管只能承载前端，不能承担持续采集；采集与通知必须在常驻或可靠调度后端运行。用户电脑关闭浏览器不影响后台。

必备：TLS、外部只暴露代理端口、数据库内部网络、非root容器、secret环境变量、上传大小/类型限制、请求超时、备份与日志轮转。URL导入防SSRF：仅允许管理员核准域，阻断内网/回环/链路本地/云metadata，每次DNS与重定向检查，浏览器子资源也受出口规则保护。解压缩限大小/层级，OCR限制像素，PDF限制页数/耗时。

采集遵守已核查的来源访问规则与频率，不绕过验证码、403或登录权限。管理员新增来源审核访问范围；合作API或导入为阻塞来源的替代方式。robots不是独立的授权证明，需记录站点约束。

Postgres每日备份、文件快照相同时间标记、7–30天保留并配置；提供实际恢复演练。任务重启后补扫与outbox恢复；部署升级先备份、迁移检查、保留回滚镜像。记录AI费用与浏览器任务资源消耗，不给出未经供应商核验的云成本报价。

## 14. 验证、试用与比赛证据

### 14.1 开发质量验收

- 从两个真实独立来源导入可验证记录，其中一个必须实际定期运行，不将同平台镜像计成两个独立渠道。
- 端到端覆盖：发现→证据→筛选→入箱→配置后的测试通道接受；登录、详情与跟进可用。
- 合成测试覆盖重复任务、通知超时、来源403/429、空解析、价格周期未知、报名与竞价不同、延期、流标重新挂牌、分组整体价和同名地址不同铺号。
- worker/API重启后既有数据、游标和待发事件不丢失；重放不产生多份业务事件。
- demo/replay/live模式界面明显区分，演示数据不混入真实试用库。

### 14.2 标注与量化目标

以下均为待验证的目标，不是已测结果。建立100–200条真实公告标注集，按网站/公告批次划分训练调参与留出测试，防同一转载跨集合泄漏。记录面积、价格周期、用途、状态、报名期限和去重标签。双人复核关键字段；试用负责人评价匹配价值。

| 指标 | 初步验收目标及口径 |
|---|---|
| 关键字段正确率 | 已给出字段值≥95%，同时报告字段覆盖率，unknown不能靠少输出刷高分 |
| 明确价格周期准确率 | ≥98%，不明确则unknown；不明周期样本单独报告误换算 |
| 匹配召回率 | ≥90%，相对于已接入来源的人工标注集合，不声称全网召回 |
| 通知准确率 | ≥80%，按负责人认为可跟进的提醒；同时报告待确认摘要 |
| 去重精确率 | ≥98%，同时报告重复漏合并率与人工审核占比 |
| 内部处理延迟 | 指定负载下快照→入队P95≤5分钟；需报告外部发现延迟与覆盖缺口 |
| 重复提醒 | 测试中同事件内部去重100%；外部通道残余重复实测统计 |
| 人工耗时 | 试用目标下降≥50%，通过同来源、同任务和时间记录比较 |

低样本结果需报告n和限制，不以小样本百分比夸大效果。百分比阈值可依据实际负载和业务需求修改，但修改记录必须保留，不能为了达标事后隐藏困难样本。

### 14.3 真实上线步骤

先访谈20分钟：确认区域/面积/预算口径、餐饮需求、常刷来源、频次、错过原因和消息渠道。管理员导入完整来源清单并标记接通/阻塞/仅导入。负责人保存真实订阅并确认候选与误报原因。

3天影子运行：仍保留人工流程，记录系统发现时间和人工发现时间，检查漏项；不承诺替代全部渠道。之后7–14天试用：每日看摘要、跟进与处理时间，每周复盘来源缺口/提醒准确率。收集具体反馈并修复，再决定扩大覆盖。

上线所需域名、服务器、消息通道凭据和试用参与由负责人提供；Codex先交付本地可运行及部署说明，不假装已接上对方账号。

### 14.4 比赛实验与开源交付

按前文评分分项规划：技术创新30%、落地30%、治理20%、发展20%；官方原文仍需赛前核对。对照A人工刷同来源，B关键词采集提醒，C本系统证据提取+实体关联+规则匹配。固定来源和时间范围，评价召回/误报/延迟/人工耗时，避免不同数据源掩盖算法差异。

可做去掉价格标准化、去掉去重、去掉证据校验的消融实验。演示包含实际采集、未知字段、来源阻塞、相同铺位重复公告、报名早于竞价和价格更新。确定性回放可展示变化，但要明确为回放。

开源核心：来源插件协议、结构化schema、价格规则、实体关联、匹配、监测和通知接口。交付许可证（建议Apache-2.0，最终核对依赖）、README中英、CONTRIBUTING、SECURITY、行为准则、Issue/PR模板、CI、版本与CHANGELOG、ROADMAP、依赖及数据许可清单。组织公开代码与私有运行数据库分离。

## 15. 风险与决策门

| 风险 | 应对及发布门 |
|---|---|
| 关键网站无法获取 | blocked状态、公开发布单位替代/授权接入；不能在演示冒充已接通 |
| 公告格式变化 | fixture合同测试、异常空结果告警、适配器版本、人工复核 |
| 错误价格/用途判断 | 原文证据、unknown、硬规则、审核，不发送确定匹配 |
| 太多无用提醒 | 两档通知、订阅反馈、合并转载、评价precision |
| 漏掉公告或后台宕机 | 分页补扫、覆盖时间、来源健康、失败提醒、常驻部署 |
| 开发范围过大 | 先纵向闭环，再多源扩展；功能不得掩盖主链路缺口 |

Go/no-go：多源真实采集、通知通道、关键字段可信、负责人愿意继续使用四项均验证后，才把“可以实际使用”作为项目结论。发现阻塞也需可审阅交付，继续完成不依赖该网站的模块。
